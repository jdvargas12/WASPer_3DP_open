1.2_Studies
    - wsp_Sm01_WASPer Study Manager [primary]
      Sources live under `Components\1.2_Studies\Sm01` as one partial component architecture. The
      GH contract/controller, toolkit-independent Manager view contract, persistent Manager window,
      seven functional tabs, Eto dialogs, canvas
      attributes, study runner, state/persistence, captured assets, and exports are separated by
      responsibility; the original component GUID is preserved for existing Grasshopper definitions.
      Persistent study editor with Galapagos-style Number Slider links, scheduled Cartesian
      iteration, global KPI capture, versioned study storage, CSV/XLSX/JSON export, and native PDF
      reports with optional viewport snapshot, KPI summary, and iteration preview. Automatic samples
      use every Grasshopper slider tick (0-7 integer domains yield 8 values); manually edited counts
      remain fixed across later updates. Its inputs
      are `wsp_path`, `kpi_sets`, `run_name`, optional `s_name`, and Gc03 `gcode`. The earlier
      `file_path`, `reset`, and `write` sockets are removed; folder browsing and both file commands
      live in the Export tab. Sm01 previews G-code by branch and
      saves every iteration under the run-local Gcodes folder. A non-empty `s_name` overrides the Study-tab property
      composer; otherwise its default creates `1_Di_3.1.3`-style names from iteration, short cell
      name, and dot-grouped X/Y/Z counts, with selectable KPI/slider properties appended.
      The Export tab displays the automatic project root
      `<GH folder>\WASPer_<definition name>` (temporary `WASPer_3DP` root when unsaved).
      Study data uses `Simulations\<run_name>`, with run-local `Gcodes`, `Snapshots`, `Reports`, and `XR` folders.
      Slider iteration and final restoration are performed only through delayed document-solution
      callbacks, preventing linked downstream objects from being expired during an active solution.
      Tabs follow `KPIs`, `G-code`, `Export`, `Study`, `Dashboard`, `Process Viewer (XR)`, `Report`.
      Process Viewer is a lightweight adapter over the current solved Gc03-enriched `wsp_path`:
      it restores the Dashboard selection through the existing recompute workflow and writes a
      revisioned external `.wasperxr` binary package to `Simulations\<run_name>\XR` by default,
      without changing the study schema. The separate
      vvvv application owns rendering and playback. The Dashboard reads
      captured study iterations directly and renders live KPI-history and parameter-vs-KPI charts
      with automatic selectors. Clicking a point highlights the same individual across both charts,
      shows its details, and selects its captured-iteration row; Ctrl-click supports multi-selection.
      The same tab also renders a Pearson correlation heatmap and normalized parallel coordinates;
      clicking a parallel line participates in the shared individual selection.
      Study and Dashboard share a persisted Study Library selector that scans
      `<save path>\Simulations\*\study.json`. Historical selections are read-only and remain
      viewable even when incompatible; schema, definition, slider identity/accuracy/domain,
      duplicate mapping, and KPI availability checks gate explicit Load/Resume actions.
      The persistent window is DPI-aware, restores DPI-tagged bounds inside the current monitor,
      records its last normal bounds as a component option when closed, and uses 1400 x 800 logical
      pixels for first-open definitions while respecting previously saved dimensions.
      It wraps command/footer controls and scales dynamic KPI groups for different resolutions.
      The KPI footer's Fabrication-units selector defaults to Auto and follows Gc03's packed
      `wsp_path.KpiUnits`; mm/cm/m overrides convert values and units consistently through captured
      iterations, Dashboard charts, data exports, and PDF reports.
      Export uses `Study name` and `Save path`; `Write with run` is enabled and blue by default and
      writes selected formats on completion, partial stop, or manual capture. Existing study names
      open Cancel/Override/Serialize; serialization finds `_1`, `_2`, and later available suffixes.
      The Study tab includes a timestamped activity console. `Run study` checks disabled KPI source
      components first and shows an owned bullet-list Yes/No warning explaining that their KPIs
      will be excluded; No is the default and cancels without changing the study.
      Study CSV/XLSX exports use three header rows: KPI type, property name, and unit.
      KPI boxes default to `wsp_path` plus `kpi_sets` first-occurrence order. Drag a box title to
      persist a custom order across Manager, study/export, and report output; `Reset order`
      restores the current input order without changing KPI selections.
      A checkbox beside each box title enables/disables the complete KPI block while preserving
      all small per-KPI selections for later restoration.
      Shared KPI schema v2 records the exact issuing component instance GUID, component GUID, and
      nickname. Every sourced box adds an independent `Run: <component nickname>` checkbox that
      automatically locks/unlocks that producer without changing block or per-KPI selections.
      Selecting Sm01 draws dotted blue arrows from the resolved KPI sources; Sm02 subsets retain
      the original producer identity, and Sm03 identifies its own component instance. Slider,
      KPI-source, and visualization arrows terminate at separate positions along Sm01's bottom
      edge and approach from below so they do not obscure its ordinary input sockets.
      Run controls occupy a dedicated header row above each KPI list. A persistent `Show values`
      footer button expands every KPI with a second value/unit line. Sm01 also serializes the last
      valid values per source instance, preserving disabled boxes, links, and values after restart.
      Expanded lists synchronize their native item height and own their two-line renderer so the
      value row survives native handle recreation and cannot be clipped;
      cached values remain excluded from new study captures and exports until re-enabled.
      Stable KPI structures update in place to prevent blank-window flashes. Source actions use a
      pale-red `Disable` button when running and pale-green `Enable` when locked. A custom
      double-buffered renderer keeps both labels visible across source-state changes.
      The Export tab also stores an iteration-snapshot profile based on Ut12/legacy Ut10: enabled
      by default, Rhino viewport, pixel width/height, DPI, and redraw wait, with a live bounded
      frame preview and a complete 420-pixel settings pane from first opening. Its split layout is
      pre-sized before applying panel minimums, preventing startup constraint errors. `Link vis component`
      persists one selected component and draws a teal canvas arrow. The Export UI instructs users
      to select one component on the Grasshopper canvas before clicking the link button. Any live
      input/output data acts as the readiness gate, including custom preview data; the selected
      viewport remains authoritative. Study schema v3 saves these settings and per-iteration
      snapshot paths. Captures live in `Snapshots`, use matching G-code basenames when available or
      the sample name without G-code, verify the PNG write, and persist a warning when capture fails;
      CSV/XLSX add `Snapshot files`.
    - wsp_Sm02_KPIs Subset
      Applies one or more identifiers to one or more KPI sets using longest-list pairing. Sm01
      displays repeated KPI types independently, for example `Thermal - Numerical (Dh)`, while
      retaining the original KPI values, units, source metadata, and semantic source keys.
    - wsp_Sm03_Custom KPIs
      Creates a Sm01-compatible KPI set from a custom type name and paired lists of readable KPI
      headers and numeric/text values. Missing headers are generated, duplicate names receive
      unique internal keys, and the summary reports all pairing corrections.

XR process-viewer export
    - Gc07 writes one atomically replaced `.wasperxr` binary package for desktop
      vvvv/VL.Stride playback and later OpenXR viewing. Its generic `geo` input is
      passed through as output zero for VLinkSend and is intentionally excluded from
      the JSON package. It exports complete path branches and point-plane orientation, roles, stroke IDs,
      available process/printability fields, units, bounds, KPIs, and cumulative
      start/end timing for every Gc03 print, travel, and Z-hop motion. Its normalized
      `sim_par` input produces printed and pending curve outputs and serializes the same
      role-aware split under `payload.simulation`; a partial input path raises a warning.
      `payload.meshes` remains an empty compatibility field, so standalone playback shows
      the fabrication path while VL.Rhino supplies heavy reference geometry in live-link mode.
    - The initial MoM workflow is predicted-process visualization only. Cerebro,
      live robot feedback, physical registration, and as-built sensing are deferred.

Packed-path common debug-output contract
    - Every active component that produces or modifies a `wsp_path` uses the same
      persistent right-click `Show all outputs` core block, in this exact order:
      `pt_planes`, `la_planes`, `flows`, `layer_h`, `layer_w`, `layer_wf`,
      `print_speed`, `print_vol`, `path_role`, `stroke_id`. Values always describe the outgoing `wsp_path`;
      unavailable optional fields stay empty, and points are represented only by
      plane origins.
    - Component-specific diagnostics follow the common block. Existing fixed
      outputs remain ahead of it: Gc03 keeps wsp_path/gcode/p_planes/t_planes,
      Pp04 keeps its visualization outputs, Gc06 keeps
      wsp_path/p_path/travels/summary, and Gc05 keeps its simulation/job-KPI
      outputs. Gc03 and Pp04 omit the duplicate core `pt_planes` socket because
      each already has a fixed plane output.
    - The contract is used throughout the Pp workflow and by Gc03, Gc05, and
      Gc06. Pr05 remains the dedicated category-based KPI inspector.

Packed G-code path workflow
    - Sl02 SlicerPlus v3 keeps the existing Curve outputs and adds hidden
      `WASPer.PathRole` metadata to every final curve: Shell, Infill, or
      Partition. This also applies to `full_path`, including its default
      collapsed `{layer}` tree. Closed Shells are automatically direction-
      normalized and align their seams to the first valid Shell through the
      corresponding layer planes; open fragments remain unchanged.
    - WasperFlowParams packs a flow assignment strategy from Pp05_Define Flow.
      Pp01_v3 accepts a list of `flow_p` strategies and evaluates the one assigned
      to each curve's role after subdivision. A strategy may target several roles,
      but no role may occur in more than one strategy; All (0) conflicts with every
      additional strategy. Unassigned roles remain at neutral flow 1.0. If
      `flow_p` is omitted, Pp01_v3 defaults to flow = 1 for every role.
    - WasperPrintPath packs canonical pt_planes, flows, layer_h, nominal LayerW,
      flow-adjusted LayerWf, per-segment PrintVol, and optional branch-aligned
      PathRoles into one wire. It also optionally stores one authoritative
      supplied `LayerPlane` per logical layer. Canonical layer-plane paths end
      at the logical-layer dimension and missing layers stay absent. This stage
      does not invent fitted/reconstructed planes; the schema leaves that future
      provenance distinct from supplied frames. Path role codes are 0 Undefined, 1 Shell,
      2 Infill, 3 Partition, and 4 Support. Each plane
      origin is the path location. The compatibility `Points` property is derived
      from those origins so point and plane geometry cannot diverge; legacy
      point-only paths are converted to World-XY planes. Its native cached wire
      preview uses the persistent WASPet palette and line thickness; its default
      is WASPer blue, with Classic, Vivid, neutral, single-color, and custom-role
      alternatives. Grasshopper's green selected-object highlight remains
      authoritative. When `role_colors` is empty, Pp04 and Sl07 also use WASPet;
      a connected local color input overrides the global palette.
    - Pp01 Path from Curves v3 is the clean toolbar component. It preserves the
      previous component GUID and complete input/output layout, so existing saved
      definitions receive the update without rewiring. It accepts `p_path`,
      optional list `flow_p`, `seg_len`, optional `ref_plane`, and
      optional `layer_w`, followed by appended `plane_mode`; it outputs `wsp_path`
      first and `summary` second. Right-click
      `Show all outputs` exposes the common outgoing-path debug block. The
      `path_role` tree is initially read from source-curve metadata. Shell curves
      carrying `WASPer.ShellSeam` are rebuilt from their canonical pre-seam loop,
      exposed through a persistent layer-scoped Shell Seam Editor, and stored with
      the updated metadata in `wsp_path.SourceCurves`. The pre-editor Pp01 source is
      archived and excluded from compilation. The original Pp01 remains
      compiled for existing definitions in `Components\5.0_Gcode\Legacy` but is
      hidden from the toolbar.
      Valid supplied `la_planes` are stored as authoritative layer reference
      frames on the outgoing wsp_path; an unavailable layer is left absent.
      `plane_mode=0` preserves automatic/multi-axis fitted and local point-below
      directions. `plane_mode=1` fixes both pt_plane Z and layer-height searches
      to `ref_plane.ZAxis` (World Z by default). Supplied `la_planes` are audited
      against fitted geometry and final frames; consolidated warnings report
      non-planarity, p95/max angular mismatch, invalid/missing planes, reversed
      normals, and fixed-axis tangent degeneracy. Per-layer details stay in
      `summary`.
      Automatic mode also classifies individual curve planarity. Planar curves
      keep a stable curve-plane normal inside aggregate non-planar layers.
      Rotated planar Infill pairs from In01/In02 use same-arclength matching only
      when their tangent and sampled transverse drift remain compatible;
      incompatible pairs use closest previous-layer height projected along the
      stable normal and produce a grey notice rather than a local-registration
      failure warning.
      Curves without WASPer.PathRole metadata are explicitly stored as
      Undefined and produce a grey notice: general All/Undefined operations
      remain valid, while Sl08 Assign Curve Roles is recommended before Pp01 when semantic roles
      are already known and Pp15 Assign Print Path Roles can assign them afterward.
      Performance uses native batch equal-arclength subdivision, one cumulative-
      length cache per sampled curve, binary correspondence lookup, lazy spatial
      fallback, full curve bounding boxes in the previous-layer RTree, and
      branch-batched DataTree writes. Summary timings separate layer analysis,
      subdivision/flow, height evaluation, and packing and report direct versus
      spatial-fallback height matches.
    - Pp03, Pp16, Pp07, and Pp08 now use the same packed path spine: `wsp_path`
      is input 0 and output 0, with `summary` as output 1. Former point/plane/flow/
      layer_h tree inputs are read from `wsp_path`; right-click `Show all outputs`
      exposes canonical plane trees and component-specific aligned diagnostics,
      without redundant point-tree outputs. Their
      previous versions remain compiled and hidden in `Components\5.0_Gcode\Legacy`,
      together with hidden Pp01 v1 and Pp04 v1.
    - Pp03-Pp08 append flattened `target_roles` / `roles` lists: 0 All paths
      (default), 1 Shell, 2 Infill, 3 Partition, 4 Support, 5 Transition,
      6 Undefined. Several role-specific values may
